# الطرفية السحابية (`/terminal`)

طرفية تعمل بالكامل في المتصفح باستخدام xterm.js، ولا تحتاج أي برنامج على جهاز المستخدم. الأوامر تُنفَّذ في Edge Function اسمها `web-terminal-exec`.

## المكوّنات
| الجزء | الملف |
|---|---|
| قاعدة البيانات | `supabase/migrations/20261101220000_web_terminal.sql` |
| الدالة السحابية | `supabase/functions/web-terminal-exec/index.ts` |
| الطرفية | `src/components/terminal/WebTerminal.tsx` و`src/pages/terminal/TerminalPage.tsx` |
| لوحة الأدمن | `src/components/admin/TerminalAdminPanel.tsx`، في تبويب "الطرفية والصلاحيات" ضمن `/admin?tab=terminal` |

النشر: `supabase functions deploy web-terminal-exec --use-api --project-ref esifpjjehdnpkhyilctv`

## كيف يُنفَّذ الأمر
1. يرسل المتصفح الأمر مع JWT المستخدم.
2. تتحقق الدالة من الـ JWT.
3. تستدعي الدالة `terminal_begin_command()`، وهي تتحقق داخل قاعدة البيانات وفي عملية واحدة من خمسة أشياء:
   - الجلسة نشطة ولم تنتهِ مدتها.
   - الصلاحية مفعّلة.
   - الحساب غير محظور.
   - لم يُتجاوز الحد اليومي ولا الكلي.
   - لم يُتجاوز حد الأوامر في الدقيقة.
   
   ثم تعدّ الأمر وتسجّله.
4. يُنفَّذ الأمر من قائمة الأوامر المعرّفة في الدالة، وتُبث المخرجات سطراً سطراً (NDJSON).
5. تُستدعى `terminal_finish_command()` لتسجيل النتيجة.

دوال العدّ والتسجيل لا يستدعيها إلا `service_role`، أي الدالة السحابية فقط. المتصفح يقرأ صفوفه فقط، ولا يكتب في هذه الجداول.

**لا يوجد shell:** لا تُنفَّذ أوامر نظام ولا SQL حر، وأي أمر خارج القائمة يُرفض.

## الأوامر
- **للجميع:** `help` و`whoami` و`status` و`quota` و`history [n]` و`date` و`echo` و`sections`، إضافة إلى `clear` و`exit` (محليّان ولا يُحتسبان).
- **للرئيس فقط:**
  - `stats` و`db health|tables|migrations` و`sessions` و`users`.
  - `grant <email> [daily]` و`revoke <email>` و`limit <email> <daily> [total]`.
  - `kill <email|session> [--ban] [reason]` و`unban <email>` و`logs [email] [n]`.

## الصلاحيات والحصص
- **الرئيس** (`team_members` بدور principal): بلا حدود وبلا انتهاء جلسة، ولا يمكن حظره.
- **المستخدمون الآخرون:** يحتاجون صفاً في `usage_quotas` يضيفه الرئيس. يرتبط الصف بالحساب لحظة الإضافة، لذلك يجب أن يكون صاحب الإيميل مسجلاً.
- **الحدود:** يومي (يُصفَّر بتوقيت عمّان)، وكلي، وبالدقيقة، ومدة الجلسة.
- **زر الإيقاف:** ينفّذه `terminal_kill()`. تغيّر حالة الجلسة يصل للمتصفح عبر Realtime فيقفل الطرفية فوراً، وكذلك سحب الصلاحية أو الحظر من الجدول، عبر trigger.
- **الجداول:**
  - `usage_quotas` للصلاحيات والحصص.
  - `user_terminal_sessions` للجلسات.
  - `terminal_command_logs` لكل الأوامر، بما فيها المرفوضة.

## ملاحظة عن اللغة
مخرجات الطرفية بالإنجليزية لأن xterm لا يعرض العربية من اليمين لليسار. الأسباب والرسائل العربية تظهر في واجهة الصفحة نفسها.

## الجسر إلى جهاز الرئيس (Claude Code وأوامر Shell)
الأوامر `claude <prompt>` و`claude` (وضع المحادثة) و`sh <command>` و`$ <command>` و`shell` (وضع الطرفية) تُنفَّذ على جهاز الرئيس عبر `scripts/local-bridge.mjs`.

- **قاعدة البيانات:** `supabase/migrations/20261101230000_terminal_bridge.sql`، وفيه جداول `bridge_devices` و`bridge_jobs` و`bridge_job_chunks`، والعمودان `allow_claude` و`allow_shell` في `usage_quotas`.
- **المسار:** يمرّ الأمر بالخطوات التالية:
  1. فحوصات `terminal_begin_command()` نفسها.
  2. التحقق من `allow_claude` أو `allow_shell`، علماً أن الرئيس مسموح له دائماً.
  3. يُنشأ صف في `bridge_jobs` موقّعاً بـ `HMAC(HMAC(BRIDGE_MASTER_KEY, 'bridge-device:'+id), payload)`.
  4. يرنّ "جرس" Realtime على القناة `bridge-<device_id>`.
  5. يستلم الجسر الأمر بمفتاح جهازه، ويتحقق من التوقيع، وينفّذ، ويبث المخرجات.
  6. يتابع المتصفح المهمة عبر Realtime، وليس عبر الدالة السحابية، لذلك لا حد زمنياً على المهام الطويلة.
- **زر الإيقاف:** إنهاء الجلسة (أو الحظر أو سحب الصلاحية أو انتهاء الوقت) يُلغي مهامها عبر trigger. الجرس يخبر الجسر فيقتل مجموعة العمليات كلها (SIGTERM ثم SIGKILL). `Ctrl+C` يوقف المهمة الحالية فقط.
- **حماية جهازك من المستخدمين الآخرين:**
  - Shell مقفل لهم في `~/.zarwa-bridge/config.json` (`shell.allowOthers: false`) حتى لو فُعّل لهم في المنصة.
  - Claude يعمل لهم بوضع `plan` للقراءة فقط (`claude.othersPermissionMode`).
  - مدة المهمة 5 دقائق لهم و30 للرئيس (`maxMinutes`).

### الإعداد لمرة واحدة
1. سر التوقيع في Edge Function secrets:
   `supabase secrets set BRIDGE_MASTER_KEY=$(openssl rand -hex 32) --project-ref esifpjjehdnpkhyilctv`
2. من `/admin?tab=terminal` اضغط **ربط جهازي**، ثم في مجلد المشروع:
   `npm run bridge -- pair <الرمز>`
3. شغّل الجسر: `npm run bridge`، أو `npm run bridge -- install-service` ليعمل دائماً في الخلفية على macOS.

الأمر `npm run bridge -- check` يفحص الإعداد والاتصال دون أن يغيّر شيئاً.

### Claude أو Antigravity لكل مستخدم
- **من يستخدم ماذا:** الرئيس يستخدم الاثنين، بـ `claude <طلب>` و`antigravity <طلب>` (أو `agy`) ووضعيهما بالاسم نفسه. لكل مستخدم آخر يختار الرئيس "وكيل الذكاء" من لوحة الأدمن: معطّل أو Claude أو Antigravity، وهذا يُحفظ في `usage_quotas.agent` و`allow_claude`.
- **أمر المستخدم:** يكتب `ai <طلبه>` فيذهب لوكيله. إن كتب اسم الوكيل الآخر يُرفض الطلب، والفحص في الدالة السحابية.
- **Antigravity:** يعمل الجسر `antigravity-ide chat --mode <mode> --reuse-window "<prompt>"`، فيُفتح الطلب في وكيل Antigravity على الجهاز. لا توجد لـ Antigravity واجهة سطر أوامر تعيد الرد، لذلك تُظهر الطرفية تأكيد التسليم فقط، والرد يبقى داخل التطبيق.
- **الأوضاع:** `antigravity.mode` (افتراضياً `agent`) للرئيس، و`antigravity.othersMode` (افتراضياً `ask`) للآخرين، وكلاهما في `~/.zarwa-bridge/config.json`.

## بوابة الموافقة على رفع التعديلات

لا أحد يستطيع تنفيذ `git commit` أو `git push` أو تغيير الفرع أو النشر من `/terminal`، لا المستخدمون ولا Claude ولا أوامر Shell. كل تعديل يمرّ بموافقة الرئيس:

1. **أثناء المهمة** يعدّل Claude الملفات داخل مجلد المشروع دون أن يطلب إذناً (`acceptEdits`). الحماية مطبّقة على ثلاث طبقات:
   - **غلاف `git`** في PATH يرفض commit/push/checkout/switch/branch/reset… وكذلك `vercel`/`supabase`/`gh`.
   - **خطّاف `reference-transaction`** يُمرَّر عبر `GIT_CONFIG_*` ويرفض أي تحديث للمراجع، حتى لو استُدعي `/usr/bin/git` مباشرة.
   - **`--disallowedTools`** في Claude. أما المستخدمون غير الرئيس فيُمنع عنهم Bash كلياً، ولا يستطيعون تعديل `.git` أو `.claude`.
2. **بعد المهمة** يقارن الجسر حالة المشروع قبل المهمة وبعدها، ويرسل الملفات التي غيّرتها هذه المهمة فقط إلى `terminal_deploy_requests`. تعديلاتك المحلية الأخرى لا تدخل في الطلب. إذا كان هناك طلب معلّق فإن الملفات الجديدة تُضاف إليه. يمكن أيضاً إرسال الطلب يدوياً بالأمر `submit [رسالة]` أو `request-push` في الطرفية، أو بالأمر `npm run bridge -- submit "رسالة"` على الجهاز.
3. **في `/admin?tab=terminal`** يظهر قسم «طلبات الموافقة على رفع التعديلات» مع عدّاد يتحدّث لحظياً. لكل طلب: الملفات، والفرق الكامل، ووصف قابل للتعديل يصبح رسالة الـ commit. تتحقق `terminal_deploy_decide()` في قاعدة البيانات من أن صاحب القرار هو الرئيس، ومن بصمة التغييرات التي راجعها.
4. **عند الموافقة** يرنّ الجرس، فيعمل الجسر فوراً:
   - يتحقق أن الملفات لم تتغير بعد الطلب، وأن الفرع هو نفسه، وأنه لا توجد commits محلية لم تُرفع بعد.
   - ينفّذ `git add` و`git commit` لتلك الملفات فقط، ثم `git push`، فينشر Vercel التعديل تلقائياً.
   - تصبح الحالة `deployed` مع الـ SHA، ويظهر إشعار في لوحة الأدمن وفي طرفية المستخدم.
   - إذا فشل الـ push يُلغى الـ commit وتبقى التعديلات كما هي، وتصبح الحالة `failed` مع السجل.
5. **عند الرفض** يعيد الجسر ملفات الطلب فقط إلى حالتها في HEAD، ويحذف الملفات التي أُنشئت، وتصبح الحالة `rejected`. إذا تغيّرت الملفات بعد الطلب تُترك كما هي.

حدود يجب معرفتها:
- Antigravity يشغّل أوامره من عملية تطبيقه، لا من الجسر، ولذلك تُطبَّق عليه طبقات مختلفة:
  - يثبّت الجسر خطّافَي `reference-transaction` و`pre-push` في `.git/hooks` الخاص بالمشروع. يرفضان أي commit أو فرع أو push يأتي من داخل `language_server` الخاص بـ Antigravity، ولا يؤثران على git الذي تشغّله أنت.
  - يوقف الجسر الوكيل فوراً إذا اقترح أمراً محظوراً.
  - الطبقتان تحميان من الخطأ، ولا تحميان من التحايل المتعمّد (مثل `--no-verify` مع push).

## Antigravity (التطبيق العادي)

Antigravity لا يملك سطر أوامر، لذلك يتصل الجسر بالخادم المحلي للتطبيق، وهو نفس الواجهة التي تستخدمها نافذته (Connect/JSON على 127.0.0.1)، ويقرأ رمز CSRF من سطر تشغيله. كل طلب يمرّ بهذه الخطوات:
1. **يبدأ محادثة** داخل مجلد المشروع (`StartCascade`).
2. **يرسل المهمة** بنموذجك الافتراضي في Antigravity (`SendUserCascadeMessage`)، ويمكن تثبيت نموذج آخر عبر `antigravity.model` في `~/.zarwa-bridge/config.json`.
3. **يبثّ الخطوات والرد** إلى الطرفية.

المحادثة تستمر بين الأسطر في وضع `antigravity`، و`/new` يبدأ محادثة جديدة. وعندما يتوقف الوكيل يُرسَل ما غيّره تلقائياً للموافقة، كما مع Claude.

تنبيهات:
- **الواجهة غير موثّقة**، فقد يكسرها تحديث للتطبيق. البديل هو `"antigravity": {"app": "ide"}` لاستخدام Antigravity IDE، وفيه يبقى الرد داخل التطبيق.
- **إعدادات تقييد الأدوات** (القراءة فقط، تعطيل الأوامر، حصر المجلدات) يتجاهلها الخادم، وقد جرّبناها فعلاً. هذا يعني أن الوكيل ينفّذ أي أمر على الجهاز، ولذلك Antigravity للرئيس فقط إلا إذا ضُبط `antigravity.allowOthers: true`.
- **يجب أن يكون التطبيق مفتوحاً ومسجَّل الدخول**، وإن لم يكن مفتوحاً يحاول الجسر فتحه.
- Shell الرئيس هو shell حقيقي على الجهاز، والحماية فيه تمنع الأخطاء ولا تمنع شخصاً يتعمّد الالتفاف عليها. لهذا يبقى Shell معطّلاً لغير الرئيس افتراضياً.

## نموذج كل وكيل والصور

- **اختيار النموذج:** من بطاقة «نموذج الذكاء لكل وكيل» في `/admin?tab=terminal`.
  - القوائم يرسلها الجسر في `bridge_devices.info.models`. قائمة Claude Code هي Opus وSonnet وHaiku (أحدث إصدار من كل منها) وFable الذي يحتاج رصيد استخدام. قائمة Antigravity هي النماذج التي يعرضها تطبيقه لحسابك، وتتحدّث كل 10 دقائق.
  - يُحفظ الاختيار في `terminal_agent_settings`، ولا يعدّله إلا الرئيس. يقرؤه الجسر قبل كل مهمة عبر `bridge_agent_settings()`.
  - «Default» يعني نموذج الوكيل الافتراضي.
- **الصور:** عندما يشير رد Antigravity إلى صورة، سواء بصيغة markdown أو برابط `file://`، يحدث التالي:
  - يرفعها الجسر إلى الحاوية الخاصة `terminal-media/<job id>/` عبر رابط رفع موقَّع يصدره `web-terminal-exec` (`action: bridge-upload`) لمهمة جارية على نفس الجهاز.
  - يُرفع فقط من مجلد المشروع أو `~/.gemini/antigravity`، وصور فقط، وبحد أقصى 10MB.
  - تتعرّف الطرفية على الإشارة `OSC 1337;ZarwaImage=…` وتعرض الصورة تحت الطرفية برابط موقَّع صالح لساعة.
  - يرى الصورة صاحب المهمة والرئيس فقط.
- **الوكلاء المساعدون:** Antigravity يشغّل بعض المهام، مثل توليد الصور، عبر وكلاء مساعدين في الخلفية. لا يُنهي الجسر الرد حتى يعود كل وكيل مساعد بنتيجته، بما في ذلك الرسائل اللاحقة التي ترسل إليه (`send_message`).

## أسئلة الوكيل (ask_question)

عندما يسأل Antigravity سؤالاً باختيارات:
1. يكتب الجسر السؤال وخياراته المرقّمة في الطرفية.
2. يرسل نسخة منه إلى الصفحة (`OSC 1337;ZarwaAsk=<base64 JSON>`)، فتعرضه بطاقة فوق الطرفية: السؤال بالعربية، وأزرار للخيارات، وحقل لإجابة حرة، وزر «تخطي».
3. يجيب المستخدم بأحد الطرق التالية:
   - بالضغط على خيار في البطاقة.
   - بكتابة رقم أو أكثر (`1,3`) في الطرفية، إذ يتحول سطر الإدخال إلى `answer ›`.
   - بكتابة إجابة حرة.
   - بكتابة `skip`.
4. تصل الإجابة عبر `bridge_job_reply()`، ولا يقبلها إلا صاحب المهمة، وفقط أثناء انتظار الجسر لها. يأخذها الجسر عبر `bridge_job_input()` ويسلّمها لـ Antigravity (`HandleCascadeUserInteraction`).
5. إذا أُجيب السؤال من داخل التطبيق، يتوقف الانتظار وتُغلق البطاقة.
